Goal Capsule

Goal Capsule

Objective: 忠实翻译必须区分“译文确有缺陷”和“审计请求自身失败”，在不牺牲全量质量覆盖的前提下降低失败率与耗时。

Product authority: STRATEGY.md 的“管道效率”和“输出质量”轨道；用户确认的分层全量审计策略。

Open blockers: 无。产品行为、降级策略、质量覆盖和性能目标均已确认。

Execution profile: 先用特征测试固定当前重试、原子重生成与状态恢复行为，再按 U1 → U5 依赖顺序实施；每个单元通过后再进入下一单元。

Stop conditions: 任何改动若需要更换模型、放宽确定性门禁、让确认缺陷进入 TTS，或破坏旧成品的原子保护，必须停止并回到产品决策。

Product Contract

Product Contract

Summary

忠实翻译将采用分层全量审计：所有片段都接受独立、精简的语义检查；确认有问题时只修复对应片段；审计服务不可用时拆小重试，最终以显式“质量审计降级”状态完成，而不是把技术故障误报为译文不合格。

Problem Frame

参考视频 STH929HARLo 的最新真实运行中，翻译接口全部返回 HTTP 200，但两个翻译片段先因输出达到长度上限而被拆分，翻译与数字修复共耗时约 4 分 36 秒。随后 8 个忠实度审计请求使用较长原文与译文，只允许精简 JSON 输出，却全部反复达到输出长度上限。

现有策略对每个审计片段重复相同请求三次。该次运行产生约 24 次无效审计尝试，任一片段最终失败就终止整条管道。失败说明审计响应容量与重试策略不匹配，不说明译文存在遗漏或增译。

8忠实翻译片段

Observed failure

“模型输出达到长度上限”被当成忠实度失败处理。相同输入重试不会改变输出长度，因此增加时间和费用，却不增加质量证据。

Key Decisions

K1. 审计基础设施故障不等于译文质量失败。 只有审计确认了遗漏、增译或误译，才将片段判为内容缺陷；超时、限流、截断和无效响应属于审计技术故障。
K2. 所有片段都进入精简语义审计流程。 不采用随机抽样或仅检查高风险片段；审计只返回是否通过及最小问题描述，技术故障无法判定的片段必须进入显式降级状态。
K3. 修复粒度是片段，最多两轮。 确认有缺陷时只重译失败片段并重新审计，保留所有已通过片段，避免整项任务重做。
K4. 降级完成必须可见。 确定性门禁通过但语义审计基础设施仍不可用时，任务可下载，但必须显示黄色“质量审计降级”状态，不能宣称完全通过。
K5. 本次不更换模型或服务商。 方案改善现有翻译与审计行为，不把稳定性建立在迁移外部平台之上。

Key Flow

每个源片段先翻译并经过确定性门禁，再进入全量语义审计。审计结果分为通过、内容缺陷和技术故障三类；三类状态有不同后续行为。

Key Flows

F1. 正常通过：全部片段完成翻译、确定性门禁和语义审计后进入 TTS，结果标记为完全通过。
F2. 内容修复：审计确认片段存在缺陷时，仅重译该片段并重新审计；两轮后仍有缺陷则停止，不生成音频。
F3. 审计自适应：审计响应截断时缩小审计单元并重试，不再原样重复无法成功的请求。
F4. 降级完成：审计技术故障持续存在、但全部确定性门禁通过时继续生成音频，并显示黄色质量提示。
Product Requirements

Product Requirements

翻译效率

IDRequirement
R1.忠实翻译必须在请求前控制片段规模，使正常片段无需依赖输出截断后的递归补救。
R2.输出截断后必须缩小工作单元再重试，不得以相同输入和相同输出容量重复请求。
R3.以缓存源材料的 29 分钟参考视频 STH929HARLo 为基准，翻译与质量审计的三次运行中位耗时不得超过 180 秒。

全量质量审计

IDRequirement
R4.忠实模式的每个源片段都必须进入语义审计流程，审计不得主动采用抽样放行；技术故障无法判定时适用 R10。
R5.语义审计必须检查遗漏、增译、误译、人物关系和限定条件，并只返回通过状态与最小问题描述。
R6.段数对应、源文本映射、数字保留、中文输出和连续未翻译英文检查必须对所有片段执行，且不依赖语义审计服务。
R7.语义审计结果必须区分“确认内容缺陷”“审计技术故障”和“通过”，不得把技术故障计入内容失败。

修复与降级

IDRequirement
R8.确认存在内容缺陷时，只重译失败片段并重新审计，最多执行两轮局部修复。
R9.两轮局部修复后仍存在确认缺陷时，任务必须失败并停止在 TTS 之前。
R10.审计技术故障必须先通过缩小审计单元恢复；仍不可用且确定性门禁全部通过时，任务可以降级完成。
R11.降级完成的音频必须可下载，同时在进度页、完成页和历史记录中显示黄色“质量审计降级”提示。

证据与状态

IDRequirement
R12.每次忠实翻译必须保存逐片段审计证据，包括最终状态、修复轮次和任何降级原因。
R13.源文本或译文发生变化后，旧审计证据不得用于证明新输出通过。
R14.页面进度必须分别展示翻译、确定性门禁、语义审计和局部修复，不得把审计等待合并成无反馈的“翻译中”。

Acceptance Examples

AE1. Covers R2, R7, R10.
  • Given: 审计响应因达到输出上限而截断。
  • When: 第一次审计失败。
  • Then: 系统缩小审计单元，不原样重复请求，也不把片段标为内容不合格。
AE2. Covers R8, R9.
  • Given: 某片段被确认遗漏一个事实。
  • When: 局部重译后重新审计。
  • Then: 只替换该片段；通过则继续，第二轮后仍失败则停止 TTS。
AE3. Covers R6, R10, R11.
  • Given: 所有确定性门禁通过，但审计服务在拆小后仍不可用。
  • When: 管道进入完成状态。
  • Then: 音频可下载，状态为黄色“质量审计降级”，且不得显示“质量审计完全通过”。
AE4. Covers R3, R4.
  • Given: 使用参考视频、已缓存源材料和当前 DeepSeek 配置连续生成三次。
  • When: 统计翻译开始至审计结束的耗时。
  • Then: 三次运行中位耗时不超过 180 秒，且每次都覆盖全部片段。

Success Criteria

  • 参考视频不再因审计响应截断而以“忠实度审计请求失败”终止。
  • 翻译与全量审计的三次运行中位耗时不超过 3 分钟。
  • 所有确认的内容缺陷都在 TTS 前修复或阻断，未经修复的缺陷不能进入 MP3。
  • 审计技术故障只能产生“降级完成”，不能产生虚假的“完全通过”或“内容失败”。
  • 审计证据可以证明每个源片段最终处于通过、修复后通过或降级不可判定状态。

Scope Boundaries

In scope

Dependencies / Assumptions

  • DeepSeek 兼容接口继续提供结构化 JSON 输出，但仍可能因输出上限、超时或服务波动失败。
  • 3 分钟指标以源材料已缓存为前提，只衡量忠实翻译与质量审计，不包含 TTS。
  • “质量保证”指已确认的内容缺陷必须修复或阻断；技术原因无法完成语义判断时必须显式降级。
  • 现有模式隔离与原子替换行为继续保护旧成品，不因本方案改变。

Key Technical Decisions

KTD1. 截断是拆分信号，不是普通重试信号

忠实翻译与语义审计都使用可配置的输入预算。初始基线分别为每个翻译单元最多 500 个英文词、每个审计单元最多 250 个英文词；响应以 finish_reason=length 结束时立即二分当前工作单元。只有超时、限流和短暂连接错误才允许对相同输入做指数退避重试，U5 可在不放宽质量门禁的前提下调节预算。

KTD2. 审计结果采用三态领域模型

每个审计单元只产生 passed、content_failed 或 technical_unavailable。聚合器收集全部结果，不让单个请求异常提前取消其他片段，也不把基础设施异常转换为质量缺陷。

KTD3. 证据由内容哈希绑定

translation_audit.json 保存版本、源文本哈希、译文哈希、逐片段最终状态、修复轮次和降级原因。只有哈希与当前材料一致时才允许恢复，避免旧审计证明新译文。

KTD4. 质量状态独立于管道状态

episode_variant 增加独立的审计状态、提示和证据路径。任务仍以 done 表示音频可下载；质量状态区分完全通过、降级和非忠实模式，避免重载现有状态机。

KTD5. 六阶段时间线不扩容

下载、转写、清洗、翻译、TTS、合并保持不变；翻译阶段增加结构化子阶段 translate、deterministic_gate、semantic_audit、local_repair 及计数，避免继续依赖自由文本猜测进度。

KTD6. 降级可交付，但不算严格质量通过

确定性门禁通过且审计技术故障无法恢复时允许生成 MP3。严格评估仍要求语义审计完整通过；降级结果会报告为可下载但未达到严格质量门槛。

High-Level Technical Design

翻译客户端负责片段预算、确定性门禁、三态审计和局部修复；流水线只消费结构化结果并在原子工作区写入证据；存储与 Web 层传播独立质量状态。确认缺陷最多修复两轮，技术故障拆小后仍不可用才进入降级路径。

Sequencing and Constraints

  • U1 先固定翻译与审计领域行为；U2 在该结果模型上增加局部修复和证据。
  • U3 完成流水线与持久化后，U4 才接入 SSE、重启恢复和历史 UI。
  • U5 最后执行真实参考视频基准；性能结果只能调节并发、片段预算和审计输出预算，不能放宽 R4、R6、R9。
  • 所有忠实模式请求共享现有速率限制器；审计不得在翻译结束后无节制地瞬时扇出。
  • 原子重生成工作区继续作为提交边界；失败和取消不得覆盖已有可下载变体。

Risks and Mitigations

Risk · model variance

模型即使输入更短也可能输出截断或无效 JSON。通过三态分类、自适应拆分和证据化降级消除错误归因。

Risk · request amplification

全量审计和局部修复可能增加调用数。使用共享限流器、只修复失败片段，并以 180 秒中位数作为退出门槛。

Risk · stale evidence

恢复流程可能复用与当前译文不一致的审计。证据必须同时匹配源文本哈希和译文哈希。

Risk · schema compatibility

SQLite 已有数据库缺少质量字段。初始化执行幂等列迁移，旧记录保留为空并按未知质量展示。

Operational and Rollout Notes

  • 部署顺序保持单进程启动时迁移：先验证数据库备份可读，再由 db.init_db() 幂等补列；不回填旧记录为完全通过。
  • 新增日志必须按阶段记录请求数、截断拆分数、技术失败数、内容失败数、修复轮次、降级原因和阶段耗时，不记录 API Key 或完整视频文本。
  • 若新审计路径导致无法接受的失败率，代码可回退，但新增 nullable 列和审计文件保持向后兼容；不得通过把降级伪装成通过来回滚。
  • 真实基准报告是发布门槛，不在服务启动时自动运行，也不依赖外部下载成功。

U1.

建立自适应翻译与三态语义审计核心

Goal
消除原样重试截断请求，并让每个审计单元产生可聚合的三态结果。
Requirements
R1–R7；F1、F3；AE1
Dependencies
无
Files
src/translation/client.py、config.yaml、tests/test_translation.py
Execution note

先为截断、技术异常和内容缺陷建立失败测试，再修改现有审计函数；保留已有数字与语言完整性特征测试。

Approach and patterns

把片段预算与审计预算放入 translation 配置；复用现有 _split_translation_segments、_split_truncated_segment、TokenBucket 和异步 semaphore。截断立即拆分，瞬态错误才走已有退避策略。审计聚合使用隔离异常的并发收集，返回结果而不是在单片段函数内抛出质量错误。

Test scenarios
  1. Covers AE1. 审计响应以 length 结束时，当前输入被拆成更小单元，且不会出现第二次相同输入请求。
  2. HTTP 超时后同一审计单元按上限重试；全部失败时返回 technical_unavailable，不返回 content_failed。
  3. 有效 JSON 报告遗漏时返回 content_failed，并保留最小问题描述。
  4. 多个审计单元中一个技术失败时，其余单元仍完成并被聚合；检查数量覆盖全部源片段。
  5. 取消信号在翻译和审计拆分递归中均能终止任务。
Verification

翻译测试证明截断不再原样重试，审计三态互斥，且每个源片段均有最终聚合结果。

Execution note

用确定性伪客户端验证“仅替换失败片段”和“两轮硬停止”，不要依赖真实模型完成单元测试。

Approach and patterns

扩展现有数字定向修复模式：语义缺陷携带审计问题重译对应源片段，之后重新执行确定性门禁和该片段全部审计子单元。证据结构记录内容哈希、原始与最终状态、修复轮次、问题摘要和技术降级原因。

Test scenarios
  1. Covers AE2. 八个片段只有第三段失败时，只对第三段发起重译并只替换第三段。
  2. 第一次修复通过时证据标记 repaired_then_passed 且轮次为 1。
  3. 第二轮后仍确认缺陷时抛出质量错误，返回内容不得进入 TTS。
  4. Covers AE3. 审计技术故障且确定性门禁通过时聚合状态为降级；确定性门禁失败时不得降级放行。
  5. 源文本或译文任一哈希变化时，旧证据不匹配并要求重新审计。
Verification

审计证据可从每个源片段追溯到最终译文、修复轮次和最终状态，且没有未经确认的质量通过。

U3.

把质量结果接入原子流水线与 SQLite

Goal
成功或降级完成后持久化质量状态，失败重生成仍保护旧成品。
Requirements
R9–R13；F1–F4；AE2–AE3
Dependencies
U2
Files
src/pipeline/orchestrator.py、src/storage/db.py、src/pipeline/state.py、tests/test_pipeline.py、tests/test_storage.py
Execution note

先增加旧数据库升级与失败重生成特征测试，确保新增字段不会破坏现有变体隔离和原子替换。

Approach and patterns

为 episode_variant 幂等增加质量状态、质量提示和审计证据路径；非忠实模式写入 not_applicable。流水线在变体工作区生成证据，只在 MP3 与工作区原子提交成功后更新最终质量字段。确认缺陷沿用失败路径，降级状态沿用完成路径。

Test scenarios
  1. 旧数据库执行初始化后新增列存在，原有变体与音频路径保持不变。
  2. 完全通过的忠实变体同时提交 MP3、审计文件和 passed 状态。
  3. 降级忠实变体状态为 done 且质量为 degraded，下载路径有效。
  4. Covers AE2. 确认缺陷在第二轮后仍失败时，不调用 TTS，也不覆盖已有完成变体。
  5. 取消或异常发生在审计后、原子提交前时，临时工作区被丢弃，旧质量状态和旧音频保持一致。
Verification

数据库重启恢复后仍能区分完全通过与降级；同模式失败重生成不产生“新质量状态 + 旧音频”的撕裂组合。

展示结构化翻译子进度与质量警告

Goal
实时、轮询和重启恢复均正确展示翻译子阶段及降级质量状态。

Approach and patterns

在现有翻译阶段内保存结构化子阶段、当前数和总数，并通过 SSE 快照、实时事件和轮询响应使用同一字段。完成事件、状态接口和历史接口携带质量状态。前端在进度卡、完成卡和历史变体中统一渲染黄色降级徽标；完全通过使用绿色提示，非忠实模式不显示。

Test scenarios
  1. 翻译、确定性门禁、语义审计、局部修复依次更新同一个翻译阶段的子阶段文本和百分比。
  2. SSE 建立晚于审计开始时，初始快照仍恢复当前子阶段与计数。
  3. 临时连接中断切换到轮询后，子阶段与质量状态不丢失。
  4. Covers AE3. 降级完成事件显示可下载按钮和黄色“质量审计降级”，不显示“完全通过”。
  5. 服务重启后状态页和历史记录从 SQLite 恢复相同降级提示。
  6. 播客版与浓缩版历史项不出现忠实审计徽标。
Verification

三种状态来源——实时 SSE、轮询、数据库恢复——对同一任务产生一致的阶段与质量展示。

U5.

建立真实视频性能基准与三模式质量验收

Goal
用参考视频证明忠实模式稳定、快速且不破坏三模式差异。
Requirements
R3–R6、R11–R13；F1、F4；AE4
Dependencies
U1–U4
Files
scripts/evaluate_mode_outputs.py、tests/test_translation.py、tests/test_pipeline.py、docs/reports/2026-07-05-faithful-audit-validation.html
Execution note

真实基准只复用已缓存的下载、转写和清洗材料；不得把网络下载或 TTS 时间计入 R3，也不得用降级运行冒充严格通过样本。

Approach and patterns

扩展现有三模式评估器，使其读取质量状态和哈希证据。使用 STH929HARLo 连续执行三次忠实翻译与审计，记录各子阶段耗时、请求数、拆分数、修复数和最终质量状态；然后对 faithful、podcast、condensed 三个变体运行严格评估并生成 HTML 报告。

Test scenarios
  1. 评估器遇到 passed 且证据哈希匹配时允许忠实质量通过。
  2. 评估器遇到 degraded 时报告音频可交付但严格质量失败。
  3. 评估器遇到旧哈希、缺段证据或确认缺陷时严格失败。
  4. Covers AE4. 三次缓存源材料运行均审计全部片段，翻译至审计结束的中位耗时不超过 180 秒。
  5. 三模式 MP3 均可解码，忠实版覆盖率、数字保留和模式差异满足既有严格阈值。
Verification

报告同时给出三次性能原始值、中位数、审计覆盖、严格质量结论与三模式输出差异，不以单次成功代替基准。

Definition of Done

Definition of Done

  • U1–U5 的测试场景均有自动化覆盖或明确的真实运行证据，完整测试集通过。
  • 参考视频三次忠实翻译与全量审计的中位耗时不超过 180 秒，且不再因审计输出截断误报译文失败。
  • 确认内容缺陷只修复对应片段，第二轮仍失败时在 TTS 前终止；审计技术故障只在确定性门禁通过后降级。
  • translation_audit.json 对所有忠实源片段保存哈希绑定的最终证据，服务重启后仍可追溯。
  • 进度页、完成页和历史记录一致显示完全通过或质量审计降级，降级 MP3 可下载但严格评估失败。
  • faithful、podcast、condensed 三模式成品均可解码，严格评估器证明内容覆盖、数字保留和模式差异符合既有阈值。
  • 下载、转写、清洗缓存继续复用；同模式失败重生成不覆盖旧成品，也不留下临时工作区。
  • 实现期间产生的废弃分支、临时日志、调试开关和未使用配置已删除，计划外重构未进入最终差异。
  • 验证结果记录在 docs/reports/2026-07-05-faithful-audit-validation.html，包含性能原始值、质量状态和未通过项。
