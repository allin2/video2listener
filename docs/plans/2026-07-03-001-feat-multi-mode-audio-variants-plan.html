Goal Capsule

目标结果：同一视频首次处理后，后续选择另一个模式只执行翻译、TTS 和合并；三个模式的输出互不覆盖，页面明确说明将复用哪些缓存，并可分别下载、重试和删除。

为什么现在做

当前 episode.video_id 是唯一键，重复检测只看视频 ID；模式特定文件写在共享目录根部，强制生成会删除并覆盖上一模式。结果是重复执行昂贵的共享阶段，且用户选了新模式仍可能得到旧模式音频。

战略一致性

该改动直接服务 STRATEGY.md 的“管道效率”和“输出质量”：降低同源内容二次生成耗时，并确保忠实、播客、精华三种内容组织方式真实可区分。

共享阶段全部复用 三种模式永久共存 唯一维度仅为 mode 同一视频串行生成

Product Contract

问题框架

用户提交同一 YouTube 链接、但选择不同输出模式时，下载、字幕/音频转写和清洗输入完全相同。系统应提示“已有源素材，将复用缓存生成新模式”，而不是把它当作同一结果的重新生成。只有用户选择已存在的同一模式时，才进入“下载已有 / 重新生成该模式”的分支。

关键产品决策

ID决策原因
K1.共享资产边界固定为下载、转写、清洗。这些步骤只依赖视频源，不依赖输出模式。
K2.模式变体边界固定为翻译、摘要、TTS 清洗、TTS 分段、合并 MP3。这些产物由模式提示词决定，必须隔离。
K3.同一 video_id + mode 只有一个当前版本。符合“只按模式”唯一化要求；音色、模型和参数变化不创建额外版本。
K4.不同模式使用“复用缓存并生成”提示；同模式才使用“下载已有 / 重新生成”。让用户准确理解操作后果。
K5.保留三个模式的全部 MP3，不因生成其他模式而覆盖或删除。支持长期比较和重复收听。

核心流程

F1. 首次处理

提交新链接 → 下载 → 转写 → 清洗 → 目标模式翻译 → TTS → 合并 → 保存共享记录和模式变体。

F2. 新模式复用

提交已处理链接 + 不同模式 → 提示将复用下载/转写/清洗 → 用户确认生成 → 前三阶段显示“复用缓存” → 仅执行模式阶段。

F3. 同模式命中

提交已处理链接 + 已存在模式 → 提供“下载已有文件”和“重新生成此模式” → 重生成只清理目标模式目录。

F4. 历史管理

历史记录按视频聚合，展开显示多个模式；每个模式拥有独立状态、下载和删除操作。

F5. 失败恢复

某模式翻译或 TTS 失败 → 共享源仍保持可用 → 只从该模式失败阶段恢复，不影响其他模式。

范围边界

本计划包含

  • 数据库增量迁移和旧数据回填
  • 模式目录隔离和共享阶段复用
  • 模式感知的提交、状态、取消、下载与删除
  • 重复提示、进度时间线和历史抽屉改造
  • 自动化测试与手工端到端验证

不包含

  • 按音色、TTS 模型或 LLM 模型保存多版本
  • 同一模式的历史快照或版本回滚
  • 云对象存储、跨设备同步
  • 同一视频多模式并行执行
  • 批量迁移旧文件到新目录

Product Requirements

ID需求验收口径
R1.一个视频只保存一份共享源记录。数据库中 episode.video_id 继续唯一；metadata、captions、clean transcript 不按模式复制。
R2.每个视频最多拥有 podcast、faithful、condensed 三个模式变体。episode_variant(video_id, mode) 唯一；模式值由服务端白名单校验。
R3.同视频新模式必须跳过下载、转写、清洗。共享文件有效时，流水线不调用 YouTube 提取器、Whisper 或 cleaner，并发送复用阶段事件。
R4.模式产物互相隔离。新产物写入 variants/<mode>/；重试或重生成不得删除其他模式文件。
R5.不同模式提交显示复用提示。提示明确列出复用下载、转写、清洗，主按钮为“生成<模式>版”，文案不出现“重新生成”。
R6.同模式命中显示已有结果选择。用户可直接下载或明确重生成该模式；重生成只覆盖该模式当前版本。
R7.状态、SSE、取消按模式定位。同一视频不同模式的状态不会串线；取消只作用于当前模式任务。
R8.历史记录展示视频下的全部模式。每个模式显示独立状态、更新时间、文件 Part 和下载入口。
R9.旧数据无损可用。升级后旧 MP3 仍能下载；迁移不移动、不改写旧文件，且不会在用户删除后被再次回填。
R10.不同模式默认串行。同一视频已有 queued/processing 任务时，另一模式返回 409 和明确提示；不同视频仍可并发。
R11.缺失或损坏缓存自动降级。数据库有记录但共享文件为空/缺失时，只从最早缺失共享阶段恢复，不误判为可复用。
R12.旧客户端在迁移期保持可用。旧下载/状态接口继续解析到默认或最近模式；新 UI 只调用模式感知接口。

反向需求

  • A1. 不允许 force=true 清理共享目录根部所有 MP3 或全部 tts_segments。
  • A2. 不允许使用 episode.mode 判断请求模式是否已有输出。
  • A3. 不允许仅靠文件名猜测模式；数据库变体记录是模式归属的权威来源。
  • A4. 不允许迁移过程批量移动用户旧文件，避免中断、同盘空间和路径回滚风险。

Planning Contract

现状取证

  • src/storage/db.py 的 episode.video_id 唯一，且共享字段与 mode/script_zh_path/audio_zh_path 混在同一行；is_duplicate() 只按 video_id。
  • src/pipeline/orchestrator.py 在共享 data_dir 根部写译文、TTS 和 MP3；force 清理会删除根部全部 MP3 和 tts_segments。
  • src/pipeline/state.py 的阶段恢复按共享目录固定文件名推断，无法区分模式。
  • src/web/server.py 的 _task_states、SSE、取消和下载都只以 video_id 为键。
  • src/web/static/index.html 只有通用 duplicate 弹窗，历史下载也只调用 /api/download/{video_id}。

关键技术决策

ID技术决策约束与理由
KTD1.新增 episode_variant，保留 episode 为共享源表。增量迁移风险最小；第一版不删除 episode 的旧模式字段，作为兼容读取。
KTD2.新增 schema_migration 并执行一次性、事务化回填。INSERT OR IGNORE 每次启动会复活用户删除的旧变体；迁移标记可避免该问题。
KTD3.旧变体零拷贝回填，新变体使用 variants/<mode>/。旧行直接引用原路径；只有重生成时才在新目录写入，不做批量文件移动。
KTD4.共享阶段和变体阶段使用两个状态对象。episode.status 表示共享源进度；episode_variant.status 表示翻译到完成，变体失败不污染共享源。
KTD5.内存任务键为 (video_id, mode)，另设 video_id 级互斥。状态与取消精确定位模式，同时落实同视频串行、不同视频可并发。
KTD6.POST /api/process 使用显式 action 两阶段确认。无 action 时只返回决策；create_variant 或 regenerate_variant 才启动任务，避免把 force 语义继续扩散。
KTD7.新状态、取消、下载路由都带 mode；旧路由作为兼容别名。消除歧义，同时允许旧页面或书签在过渡期继续工作。
KTD8.缓存有效性以数据库路径 + 非空文件检查为准。不能只依赖 DB 状态；共享文件缺失时必须重新执行最早缺失阶段。

目标数据模型

CREATE TABLE IF NOT EXISTS schema_migration (
  name TEXT PRIMARY KEY,
  applied_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS episode_variant (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  video_id TEXT NOT NULL,
  mode TEXT NOT NULL CHECK (mode IN ('podcast','faithful','condensed')),
  status TEXT NOT NULL DEFAULT 'new',
  variant_dir TEXT,
  script_zh_path TEXT,
  summary_path TEXT,
  tts_text_path TEXT,
  tts_segments_dir TEXT,
  audio_zh_path TEXT,
  error_message TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  UNIQUE(video_id, mode),
  FOREIGN KEY(video_id) REFERENCES episode(video_id) ON DELETE CASCADE
);
CREATE INDEX IF NOT EXISTS idx_episode_variant_updated
  ON episode_variant(updated_at DESC);

迁移约束：_get_conn() 必须启用 PRAGMA foreign_keys=ON。迁移事务先建表、再回填、最后写入迁移标记；任一步失败均回滚。已有 episode 列第一版不删除。

API 契约

接口用途关键响应/行为
POST /api/process预检或启动无 action：返回 queued、reuse_available 或 variant_exists。带 create_variant/regenerate_variant：启动任务。
GET /api/status/{video_id}/{mode}轮询状态返回目标模式状态、共享复用信息、阶段数组和输出路径。
GET /api/status/{video_id}/{mode}/streamSSE 进度共享阶段发送 stage_reused，变体阶段发送现有 stage 事件。
POST /api/cancel/{video_id}/{mode}取消模式任务只设置该模式 cancel_event；不清理其他模式。
GET /api/download/{video_id}/{mode}下载指定模式从 variant 行读取主 MP3；多 Part 由任务列表给出独立索引。
GET /api/tasks历史聚合一条视频记录含 variants[]，每项有 mode/status/parts/updated_at。
DELETE /api/tasks/{video_id}/{mode}删除单个变体新目录可整体删除；零拷贝旧变体只删 DB 行，不碰共享根目录文件。
DELETE /api/tasks/{video_id}删除整个视频强确认后删除所有变体记录和源记录；文件清理遵循显式安全策略。

状态与恢复规则

  1. 先调用共享资产解析器，逐项验证 metadata、字幕/音频和 clean transcript。
  2. 共享完整时，将下载、转写、清洗标记为 reused/done，不调用对应处理函数。
  3. 读取目标 variant；不存在则创建 new，存在且 action 为 regenerate 时只清理其 variant_dir。
  4. 变体状态仅由目标模式目录文件推断；check_stage_file() 接受 shared_dir 和 variant_dir，禁止扫共享根部 MP3。
  5. 取消或失败保留有效共享资产；翻译失败可从 shared-ready 重试，TTS 失败可从 translated 重试。

风险与缓解

风险影响缓解
迁移错误关联旧模式旧文件下载到错误模式仅使用 episode.mode 回填一条变体；记录迁移日志；不根据文件名猜测。
共享状态被变体失败覆盖下次错误重跑下载/转写共享与变体更新函数分离；异常路径只写 variant。
force 清理越界其他模式 MP3 丢失删除函数只接收 variant_dir，并加路径归属断言与回归测试。
旧 SSE/状态路径串线UI 显示另一模式进度统一 task_key(video_id, mode) helper；所有读写均通过 helper。
旧文件不在 variants 目录删除语义危险legacy variant 标记为零拷贝；单模式删除不删除根目录物理文件。

Implementation Units

U1. 数据库迁移与变体存储层

依赖：无 · 覆盖：R1, R2, R9, R11 · 关键决策：KTD1, KTD2, KTD3

目标：建立共享 episode + 模式 variant 的持久化边界，并安全承接现有数据。

文件

  • src/storage/db.py — schema、迁移、variant CRUD、聚合查询
  • tests/test_storage.py — 新增迁移和 CRUD 测试

实施步骤

  1. 在每个连接启用 foreign keys；创建 schema_migration 和 episode_variant。
  2. 事务内执行 episode_variant_v1 回填：每条旧 episode 最多生成一条 mode 变体，路径原样引用；根据 audio/script 是否存在推断 done/translated/failed。
  3. 迁移成功后写 marker；再次启动不得重复回填。
  4. 新增 get_variant、list_variants、upsert_variant、update_variant_status、delete_variant；限制可更新字段白名单，避免动态 SQL 注入。
  5. 将 duplicate 查询替换为“共享是否存在”和“指定模式是否完成”两个明确函数；保留旧函数一段时间但不用于新流程。

测试场景

  • 空数据库初始化后两张新表和索引存在。
  • 旧 done episode 回填为对应模式 done variant，路径不改变。
  • 迁移二次运行不新增行；删除回填 variant 后重启不会复活。
  • 同 video + mode 重复 upsert 更新一行；不同 mode 共存三行。
  • 删除 episode 级联删除 variant；非法 mode 被拒绝。

完成信号：迁移可重复启动且数据无损，variant CRUD 不再读写 episode 的旧模式字段。

U2. 共享/变体路径与阶段状态重构

依赖：U1 · 覆盖：R3, R4, R9, R11 · 关键决策：KTD3, KTD4, KTD8

目标：让文件系统状态检测明确区分共享目录和目标模式目录。

文件

  • src/pipeline/state.py — 共享阶段与变体阶段检查
  • src/pipeline/orchestrator.py — 路径 helper 和 legacy 解析
  • tests/test_pipeline.py — 状态推断、旧路径和隔离测试

实施步骤

  1. 新增 variant_dir(data_dir, mode) 和合法模式校验，所有新模式产物只从该 helper 派生。
  2. 拆分 check_shared_stage_files(data_dir) 与 check_variant_stage_files(variant_dir)；MP3 仅在 variant_dir 扫描。
  3. 将 _existing_stage_paths 拆成 shared 恢复和 legacy variant 恢复，避免把根部任意 MP3 关联到新模式。
  4. 输出文件名追加 mode，保证用户下载后也能区分，例如 <title>_condensed.mp3。

测试场景

  • faithful MP3 存在时 condensed 仍为 new。
  • 旧根部 MP3 只被迁移记录指定的 mode 识别。
  • 脚本更新时间晚于目标 mode MP3 时仅该 mode 的 TTS 状态失效。
  • 共享 transcript 缺失时三种模式都不能标记为 source-reused。

U3. 流水线复用、重生成与失败恢复

依赖：U1, U2 · 覆盖：R3, R4, R7, R10, R11 · 关键决策：KTD4, KTD5, KTD8

目标：把 orchestrator 变为“确保共享源就绪 → 处理目标变体”，消除跨模式覆盖。

文件

  • src/pipeline/orchestrator.py — 两阶段编排、变体状态写入、范围化清理
  • src/pipeline/state.py — 状态枚举/恢复支持
  • tests/test_pipeline.py — mock 调用次数和恢复回归

实施步骤

  1. 提取 ensure_shared_source()：只在共享文件缺失时执行 extractor/transcriber/cleaner，并只更新 episode。
  2. 提取 process_variant()：翻译、摘要、TTS、merge 都接收 variant_dir，并只更新 episode_variant。
  3. 把 force 替换为内部明确 action；regenerate_variant 只调用 cleanup_variant_outputs(variant_dir, resume_from)。
  4. 共享缓存命中时发送三条结构化复用消息/事件，供 UI 标记阶段完成。
  5. 以 video_id 级锁串行不同 mode；锁释放必须放在 finally。任务结果携带 mode 和模式下载路径。
  6. 异常和取消只更新目标 variant；共享阶段失败时才更新 episode 共享状态。

测试场景

  • 已有完整 shared + faithful，新建 podcast 时 extractor/transcriber/cleaner 调用次数均为 0，translator/TTS 各执行一次。
  • 重生成 podcast 后 faithful 的脚本、segments、MP3 hash 与 mtime 不变。
  • podcast 翻译失败不改变 faithful done，也不使 episode shared 失效。
  • 同视频第二模式并发提交被拒绝；不同视频可同时处理。
  • 共享 transcript 丢失时从转写/清洗阶段恢复，而不是盲目复用。

U4. 模式感知任务状态与 API

依赖：U1, U3 · 覆盖：R5, R6, R7, R10, R12 · 关键决策：KTD5, KTD6, KTD7

目标：让提交决策、运行状态、SSE、取消和下载都精确指向模式。

文件

  • src/web/server.py — task key、process 决策、模式路由、兼容路由
  • tests/test_web.py — API/SSE/并发/兼容测试

实施步骤

  1. 引入唯一 _task_key(video_id, mode) helper；改造 _get_task_state、_set_task_state、SSE 发射和 progress append，禁止散落字符串拼接。
  2. POST /api/process 先做 variant 决策：同模式完成 → variant_exists；不同模式且 shared 有效 → reuse_available；首次提交直接 queued。
  3. 只接受与决策匹配的 action：不存在模式只能 create_variant，已存在模式只能 regenerate_variant；错误组合返回 409。
  4. 新增带 mode 的 status/SSE/cancel/download 路由；完成事件、错误事件均包含 mode。
  5. 旧无 mode 路由解析顺序：活跃任务 → episode 旧 mode → 最近更新的 done variant；响应增加 deprecation 日志，不影响现有书签。

测试场景

  • 不同模式返回 reuse_available 和 reused_stages，不启动线程。
  • 同模式返回 variant_exists 和正确 download_url。
  • 确认 action 后只创建一个线程；重复确认受并发锁保护。
  • 取消 faithful 不触发 podcast cancel_event。
  • 旧下载接口在只有一个或多个 variant 时按兼容规则返回可预测文件。

U5. 提交提示与复用进度体验

依赖：U4 · 覆盖：R5, R6, R7 · 流程：F2, F3, F5

目标：让不同模式生成与同模式重生成在界面上成为两个语义清晰的操作。

文件

  • src/web/static/index.html — 复用弹窗、duplicate 弹窗、模式状态路由、时间线复用样式
  • tests/test_web.py — 静态契约和关键文案测试

实施步骤

  1. 保留同模式弹窗：说明已存在目标模式，按钮为“下载已有”和“重新生成此模式”。
  2. 新增 reuse_available 弹窗：说明“已找到该视频的源素材，将复用下载、转写、清洗”；主按钮为“生成精华浓缩版”等具体模式，次按钮取消。
  3. 确认后发送对应 action；会话存储同时保存 videoId 和 mode，刷新恢复调用模式状态路径。
  4. 时间线支持 reused 状态：绿色完成节点，元信息显示“复用缓存”，持续时间不伪造为本次耗时。
  5. 结果页下载、新任务返回和错误重试均保留/传递当前 mode。

测试场景

  • 新模式提示文案不含“重新生成”，且明确列出三项复用阶段。
  • 同模式弹窗下载 URL 含 mode；重生成 action 正确。
  • 刷新处理中页面后恢复到相同模式任务，不显示另一个模式状态。
  • 复用阶段显示“复用缓存”，翻译/TTS 继续显示真实进度。

U6. 历史聚合、模式下载与安全删除

依赖：U1, U4 · 覆盖：R8, R9, R12 · 流程：F4

目标：把历史抽屉从“一视频一模式”升级为“一视频多变体”。

文件

  • src/storage/db.py — episode + variants 聚合查询
  • src/web/server.py — variants[]、Part 检测、模式删除
  • src/web/static/index.html — 分组展示、独立下载/删除
  • tests/test_web.py — 历史响应和删除安全测试

实施步骤

  1. GET /api/tasks 返回视频级元数据和 variants[]；Part 扫描限制在 variant_dir，legacy 变体使用已登记 audio path 所在目录。
  2. 前端每个视频行展示已有模式徽标，展开后每个变体独立显示状态、时间、下载与删除。
  3. 模式删除：拒绝活跃任务；新 variant_dir 校验必须位于 data_dir/variants 后才可递归删除；legacy 变体只删 DB 行。
  4. 整视频删除使用更强确认文案，明确会影响全部模式；先拒绝任一活跃 variant，再按既有安全策略清理。

测试场景

  • 一个 episode 返回三个 variants，顺序稳定，Part 归属正确。
  • 删除 condensed 不影响 faithful/podcast DB 行和文件。
  • 路径逃逸或不在 variants 根下时拒绝递归删除。
  • legacy variant 删除后重启不会被迁移重新创建。

U7. 兼容收口与端到端验证

依赖：U1–U6 · 覆盖：全部需求 · 执行边界：不删除旧列

目标：证明新旧数据、三种模式和所有恢复路径可用，再允许后续清理旧字段。

文件

  • tests/test_storage.py、tests/test_pipeline.py、tests/test_web.py — 完整回归
  • docs/plans/DOD_STATUS.md — 实施阶段按仓库惯例更新完成证据（不在本规划阶段修改）

实施步骤

  1. 构造旧版 SQLite fixture + 根部文件布局，执行启动迁移和下载验证。
  2. 构造同视频三模式端到端 mock，断言共享函数只调用一次、输出路径和内容分别对应模式。
  3. 验证 SSE 与轮询在刷新、短暂断线、取消和失败恢复场景中的 mode 一致性。

部署与回滚

  1. 升级前复制 SQLite 文件；无需复制全部媒体文件，因为迁移不移动它们。
  2. 先部署数据库/兼容读取，再启用新 UI；单体应用可一次发布，但实现提交按 U1→U7 顺序保持可回滚。
  3. 若新流程故障，回滚应用代码仍可读取原 episode 字段；新增表保留不影响旧代码。
  4. 不得通过删除 episode_variant 回滚用户新生成的模式文件；恢复时优先修复代码并保留数据。

Definition of Done

  • R1–R12 与 A1–A4 均有对应自动化或手工验收证据。
  • 数据库迁移在真实旧版 fixture 上验证幂等、无文件移动、无路径丢失。
  • 同视频三模式生成只执行一次共享阶段，三份 MP3 永久共存且下载正确。
  • 不同模式提示使用“复用缓存并生成”语义，同模式提示使用“下载已有 / 重新生成”语义。
  • 重生成、失败、取消、删除均不会修改其他模式或有效共享资产。
  • SSE、轮询、刷新恢复、结果页、历史抽屉都按 video_id + mode 工作。
  • 旧下载和状态接口在兼容规则下继续工作，并记录弃用日志。
  • 全量测试通过，手工验收矩阵完成，未引入新的未解决阻塞项。
  • 旧 episode 模式字段未在本次删除；后续清理作为独立计划。
