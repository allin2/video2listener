Grounding Context

Codebase Context

video2listener — YouTube → 中文 MP3 播客转换器。Pipeline: yt-dlp → whisper → DeepSeek translate → MiMo/Edge TTS → ffmpeg merge。核心瓶颈：翻译阶段串行迭代批次（client.py:394 for 循环），TTS 阶段 ThreadPoolExecutor(3) 内嵌 MiMo 每段又创建 ThreadPoolExecutor(1)（synthesizer.py:198）。翻译和 TTS 完全顺序执行，无重叠。

External Research (research value: high)

DeepSeek API 支持 500 并发连接，async dispatch 实测 2x 吞吐（187 vs 92 req/min）。Edge TTS 实测上限 3-5 并发 WebSocket。Producer-consumer 阶段重叠可节省 ~40% 端到端延迟。OpenAI AsyncOpenAI 客户端原生支持非阻塞调用。TCP AIMD 自适应并发是经过验证的分布式系统模式。

Past Learnings

TTS 并发（ThreadPoolExecutor 3 workers）已验证可将 TTS 阶段从串行加速 ~3x。翻译批处理（batch_size=5）已减少 API 往返次数。后台守护线程模式（orchestrator.py:488）已验证异步任务不阻塞主路径。

Ranked Ideas

#1 Async Fan-Out #2 Producer-Consumer #3 Remove Nested Executors #4 Adaptive Concurrency #5 Progressive Output #6 Token-Aware Batching #7 Cancel Tokens

1Async Translation Fan-Out — 并发 API 调度

1. 翻译并发化 Confidence 90% Complexity Medium

Description: 将 client.py:394 的串行 for batch in batches 替换为 AsyncOpenAI + asyncio.Semaphore(10) 并发调度。所有翻译批次同时发出，通过信号量控制最大并发数。DeepSeek 支持 500 并发连接，当前只用 1。同时将 retry 中的 time.sleep() 改为 asyncio.sleep() 实现非阻塞退避。

Basis: direct: client.py:394 串行 for 循环；client.py:190 time.sleep() 阻塞整线程。external: DeepSeek 500 并发连接限制；async dispatch 2x 吞吐（Baidu 基准测试 187 vs 92 req/min）。

Rationale: 翻译阶段是最大延迟源（40 段 × 5 批 = 8 次串行 API 调用，每次 ~500ms → 4s 纯等待）。并发化后所有批次同时发出，延迟降至单次 API 调用的延迟（~500ms），4-6x 加速。这是所有方案中影响最大的单项改动。

Downsides: 需要从同步 OpenAI 切换到 AsyncOpenAI；需测试 DeepSeek 免费 tier 的 RPM 限制；高并发下需配合 rate limiter（见 #4）避免 429 风暴。

2Producer-Consumer Pipeline — 翻译与 TTS 阶段重叠

3. 阶段流水线化 Confidence 85% Complexity Medium

Description: 在 orchestrator.py:441-513 的翻译 → TTS 边界引入 asyncio.Queue（maxsize=8）。翻译每完成一批即入队，TTS worker 池从队列拉取并开始合成。两个阶段重叠执行——TTS 不再等翻译全部完成。类似丰田 Kanban 系统：下游拉取，上游不堆积。

Basis: direct: orchestrator.py:500 _should_run(TTS_DONE) 强制 TTS 等待全部翻译完成。external: Producer-consumer overlap saves ~40% end-to-end；Toyota Kanban pull system。reasoned: 翻译和 TTS 使用不同资源（LLM API vs TTS API），可并行而不争用。

Rationale: 对 20 分钟视频（翻译 90s + TTS 60s），从 150s 串行降至 ~95s，节省 ~37%。不改变任何 API 行为，纯架构优化。翻译和 TTS 是独立 I/O 操作，重叠执行没有资源竞争。

Downsides: 需要重构 orchestrator 的阶段控制流；Queue 有界性需要调优（太紧浪费吞吐，太松浪费内存）；错误传播需要仔细设计（翻译失败时 TTS 已开始的部分如何处理）。

3移除嵌套 Executor — 统一事件循环架构

5. 架构减负 Confidence 95% Complexity Low

Description: 消除 TTS 路径的双层线程池：synthesizer.py:198 的 MiMo ThreadPoolExecutor(1)（仅为 timeout 存在）+ synthesizer.py:75 的外层 ThreadPoolExecutor(3)。改为单层线程池，用 future.result(timeout=300) 直接在外层 future 上设置超时。Edge TTS 的 asyncio.run() 每段创建/销毁事件循环（synthesizer.py:257）改为共享持久循环。

Basis: direct: synthesizer.py:198 TPE(1) 嵌套在 TPE(3) 内；synthesizer.py:257 asyncio.run() 每段新建循环。reasoned: 嵌套 executor 产生 (3×1) 线程 + O(N) executor 构造开销；asyncio.run() 每次 ~5-20ms 循环创建开销，200 段 = 1-4s 纯浪费。

Rationale: 移除无价值的线程嵌套，简化调用栈从 4 层到 2 层。消除 per-segment executor 分配（200 段 = 200 次 TPE 构造）。使线程模型可预测，为 #1 和 #2 的异步化铺平道路。风险极低——纯简化不改行为。

Downsides: MiMo timeout 机制需要从 executor 迁移到 threading.Timer 或 asyncio.wait_for；需要验证 Edge TTS 共享事件循环下的线程安全性。

4Adaptive Concurrency Discovery — TCP 式自适应并发

2. TTS 并发与引擎 4. 超时与重试策略 Confidence 75% Complexity Low

Description: 用 AIMD（加法增加/乘法减少）算法替代硬编码的 batch_size=5 和 TTS concurrency=3。启动时保守（并发=2），每次成功后 +1，收到 429 后减半。系统自动发现 DeepSeek 和 Edge TTS 的实际速率上限，无需手动调优。类似 TCP 拥塞控制：探测上行，碰撞回退。

Basis: direct: client.py:334 batch_size=5 硬编码；synthesizer.py:38 concurrency=3 硬编码。external: TCP Reno/NewReno AIMD (Jacobson 1988) 是最成熟的 adaptive 算法。reasoned: 不同部署环境的速率限制不同（免费 vs 付费 API key、代理延迟、TTS provider），硬编码必然在某些环境下次优。

Rationale: 消除手动调优步骤。用户切换 API key、更换 TTS provider 或部署到不同网络环境时无需改配置。DeepSeek 免费 tier（~20 RPM）和付费 tier（~200 RPM）的上限差异巨大——自适应并发对两者都有效。

Downsides: 初始阶段吞吐偏低（需 warm-up 到最优并发）；AIMD 在突发流量下可能震荡；需要监控 429 响应的粒度（有些 API 返回 Retry-After header，有些不返回）。

5Progressive MP3 Output — 渐进式流式输出

3. 阶段流水线化 Confidence 80% Complexity Medium

Description: 不等管道完成就输出音频。每完成一个 TTS segment，立即将其 MP3 帧追加到输出文件（MP3 帧自带同步字，无需重新编码即可拼接）。用户提交 URL 后 5-10 秒就能听到开头内容，而不是等 5 分钟。前端用 HTTP Range 请求或 chunked transfer 逐步加载。

Basis: direct: orchestrator.py:524-540 merge 在管道末尾才执行。reasoned: MP3 每帧 26ms 自带 sync word + header，字节级拼接无需 ffmpeg 重编码。reasoned: 感知延迟比实测延迟更影响用户体验——5 秒听到声音 vs 5 分钟后听到，产品感知天差地别。

Rationale: 这是感知延迟改善最大的单项改动。将用户心智模型从"批处理作业"变为"流媒体服务"。10 秒内出声音，即使完整管道仍需 60 秒，用户已开始收听。配合 #2（Producer-Consumer Pipeline），前几段在翻译开始后几乎立即可用。

Downsides: 需要 CBR（恒定比特率）MP3 编码；进度条可能不均匀（前段快后段慢）；部分播放器对不完整 MP3 的 VBR header 兼容性差；需要最终 ffmpeg fixup 写入正确的时长元数据。

6Token-Aware Adaptive Batching — 按 Token 数打包批次

1. 翻译并发化 Confidence 85% Complexity Low

Description: 用 tiktoken 计算每个 segment 的 token 数，贪心装箱算法将 segments 打包到接近 max_tokens=4096 上限的批次，替代固定 batch_size=5。短 segment（对话密集的视频）可一批装 15-20 段，减少 API 调用次数 40-60%。同时预先检测超长 segment，主动拆分而非等 API 返回 truncation 后才被动处理。

Basis: direct: client.py:334 batch_size=5；config.yaml max_tokens: 4096。reasoned: whisper segment 长度方差极大（2 秒 vs 40 秒 → token 数差 10x）；固定 batch_size=5 对短段浪费 token 预算，对长段有 truncation 风险。direct: client.py:263-280 TranslationTruncatedError 触发昂贵的 fallback_sequential——预先检测可避免。

Rationale: 与 #1（Async Fan-Out）互补：#1 解决 API 调用的并发度，#6 减少 API 调用的总量。两者叠加效果倍增。预检测防止 truncation → fallback 的最坏情况（一批失败 → N 次串行重试，延迟放大 10x+）。

Downsides: tiktoken 增加 ~1ms per-segment 开销；贪心装箱不能保证最优打包；大 batch 可能影响翻译质量（上下文稀释）——需要 A/B 测试验证质量边界。

7Cancel Token Propagation — 阶段内取消响应

4. 超时与重试策略 Confidence 90% Complexity Low

Description: 当前取消检查仅在阶段之间（orchestrator.py:424-429），用户在 40 段翻译中点击取消需等到全部完成才能响应。将 cancel_event（或 asyncio.Event）注入每个翻译批次和 TTS segment 的循环内部，每次迭代检查 is_set()。设置 per-batch deadline（15s）防止卡住的 API 调用无限期阻塞取消。

Basis: direct: orchestrator.py:424-429 _check_cancel 只在阶段间运行。reasoned: click-to-cancel 延迟 = 当前阶段剩余时间（最长可达数分钟），在 40 段翻译中点击取消等于无用。direct: orchestrator.py:488 已有 daemon thread cancel 模式可以参考。

Rationale: 响应式取消是 UX 基础设施。用户误提交 2 小时视频不应被强制等待或杀进程。配合 #1 的 asyncio 架构，CancelledError 自然传播，实现成本极低。是让其他加速方案"安全可取消"的前提——并发越高，越需要能随时停止。

Downsides: 取消粒度需要在"每段检查"（频繁但安全）和"每批检查"（高效但延迟）之间权衡；取消后已完成的 TTS segment 如何清理需要设计。
